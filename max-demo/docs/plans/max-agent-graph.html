Max agent graph

How Max works as a teammate on LangGraph: seven nodes, the tool loop, the pause for a human approval, the safety rules that sit in code, and the parts around the graph that keep it fast and safe to repeat.

No code yetModel: config switch (Gemini here, Qwen elsewhere)State: SQLite (max.db + checkpoints.db)

What changed since v1

  • 9 nodes → 7: intake now also picks the tools; respond now also writes the audit record.
  • Simple reminders left the graph: the job runner posts them with no AI and no saved run.
  • A safety gate in prepare_approval checks recipients, attachments and links in code. A blocked step goes back to the agent as a result.
  • Email is drafted before approval and only that draft is sent, once. One click wins.
  • Teams gets an answer straight away; the work runs in the background, one run per thread.
  • Every tool call gets a result before the model is called again (Change, Cancel and blocks included).
  • Dates ("tomorrow", "Friday") are worked out in code, in the team's time zone. (v1's "Sat 22 Nov" was a Sunday.)

The graph

Every request that needs thinking runs through this graph. Max thinks in agent, uses read tools in a loop, and stops at await_approval before anything leaves the team.

Nodes

Safety rules in code

The approval click is the last check, not the only one. These run in prepare_approval and execute no matter what the model says, so a file or email that tries to steer Max can't get anything out.

Company recipients onlyEvery to, cc and bcc must be a person in the company. Outside addresses are always blocked.
Attachments from the team driveOnly files from the team's SharePoint folder, each listed on the card by name and size.
The card shows everythingPlain text: to, cc, bcc, reply-to, subject, full body, every link written out, and a note if outside content was read.
Send what was shownThe approved payload is frozen and matched by hash. No model call between Approve and send.
Events can't sendRuns started by an incoming email or a file change get no sending tools. They can only suggest something in the thread.
Approver checked on the serverThe click's user id must be the requester or the manager. Hiding buttons is only a convenience.

Around the graph

Three pieces keep the graph fast and safe to repeat: a gate that answers Teams at once and drops duplicates, a queue that runs one request per thread, and a job runner for anything timed.

The approval pause

Waiting can take hours, so the run is saved and ends. The click is answered at once, and the run resumes in the background.

Example: on Monday 23 Nov, "@Max set up 30 minutes tomorrow with Prince and Daniel about the pilot"

  1. gate: replies at once (typing), queues the run for this thread.
  2. intake: Karthi asked in the Budget thread; tools = find_free_times, search_memory, create_meeting. Code works out that tomorrow is Tuesday 24 Nov (team time zone).
  3. agent (model call 1): asks for free times and for notes about the pilot.
  4. tools: free slots for all three on Tue 24 Nov at 10:00 and 14:00; two pilot notes.
  5. agent (model call 2): proposes 10:00 with a short agenda.
  6. prepare_approval: all three are company people, so rules pass. Card: "Pilot follow-up · Tue 24 Nov 10:00-10:30 · Karthi, Prince, Daniel · Teams link · agenda". Expiry job set.
  7. await_approval: paused. Karthi clicks Approve; the click is answered at once.
  8. execute: slot still free; Max creates the event in its own calendar (invites go out), schedules the 15-minute reminder in the thread (Tue 09:45); the 24-hour one is skipped because the meeting is less than a day away.
  9. agent (model call 3) writes the confirmation; respond posts it and logs 3 model calls, 3 tool calls, 1 approval.
